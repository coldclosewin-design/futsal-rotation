# 풋살 키퍼·휴식 배정 웹페이지

6~12명이 참가하는 풋살 경기에서 `키퍼`와 `휴식`을 공평하게 자동 배정해주는 정적 웹페이지입니다.  
별도 서버 없이 HTML, JavaScript, CSS만으로 동작하며, GitHub Pages로 바로 배포할 수 있습니다.

## 최근 업데이트

### 1. 모바일 결과표 가독성 개선
- 모바일에서 이름이 중간에 줄바꿈되던 문제를 수정했습니다.
- 결과표 셀은 한 줄 기준으로 유지되고, 화면이 좁으면 표 전체를 가로 스크롤해서 볼 수 있습니다.
- 긴 이름도 더 안정적으로 확인할 수 있습니다.

### 2. 늦참·조기퇴장자 배정 공정성 개선
- 기존에는 늦게 오거나 일찍 가는 인원이 `키퍼/휴식`을 덜 맡고 필드 위주로 배정되는 경향이 있었습니다.
- 이제는 각 인원의 실제 참여 쿼터 수를 기준으로 `키퍼/휴식` 부담이 비슷한 비율로 분배되도록 로직을 개선했습니다.
- 부분 참가자가 포함된 경기에서도 특정 인원에게 부담이 과도하게 몰리는 현상을 줄였습니다.

### 3. 회귀 테스트 반영
- 자동 테스트 기준 `91 PASS, 0 FAIL`
- 기본 인원 구성, 부분 참가, 에러 케이스, 카카오톡 공유 포맷까지 함께 검증합니다.

## 주요 기능

- **엄격 연속 금지**: 같은 사람이 연속 쿼터에 `GK`, `Rest`로 배정되지 않도록 최대한 방지
- **공평한 배정**: 전체 참가자와 부분 참가자를 모두 고려해 `키퍼/휴식` 부담 분산
- **부분 참가 지원**: 참가자별 `Q시작 ~ Q끝` 설정 가능
- **카카오톡 복사**: 결과를 바로 공유할 수 있는 텍스트 형식 제공
- **멤버 관리**: `members.json` 기반으로 참가자 목록 유지
- **서버 불필요**: 정적 파일만으로 운영 가능

반드시 HTTP 서버로 실행해서 확인하세요.

## 인증

Supabase 설정 후 홈에 처음 접속하면 팀 PIN 입력창이 표시되며, 올바른 PIN을 입력하면 로그인 상태가 브라우저에 저장되어 새로고침해도 유지됩니다.
인증 바의 **회장 로그인**에서 비밀번호를 입력하면 팀 세션을 로그아웃한 뒤 회장 세션으로 전환하며, **로그아웃**하면 팀 PIN을 다시 입력해야 합니다.
`js/config.js`의 Supabase URL 또는 anon key가 비어 있으면 홈과 투표 화면은 자동으로 데모 모드로 동작합니다.

## 주간 참석 투표와 공용 데이터

`vote.html`에서 내 이름을 선택하고 **참석 / 불참**을 누르면 현황과 가능 포맷·휴식 인원이 갱신됩니다.
이름은 `localStorage`의 `exican_member_id`에 저장하고 **변경**으로 다시 고릅니다.
실제 모드는 팀 로그인이 필요하며 회장 도구는 인증 역할 `admin`일 때만 표시합니다.
이름 선택은 인증 권한을 바꾸지 않으며, 실제 쓰기 권한은 Supabase RLS가 검사합니다.

투표 창은 경기 전 일요일 13:00부터 월요일 13:00까지(KST)입니다.
예정·취소 상태에서는 버튼을 비활성화하고, 마감 후에는 벌금 안내와 함께 투표를 허용합니다.
지각 여부는 DB 트리거가 반환한 `is_late`를 사용합니다. 회장은 취소/복구와 수동 생성을 할 수 있습니다.
수동 생성은 오늘을 포함한 다가오는 토요일을 대상으로 하며 이미 있으면 중복 안내를 표시합니다.

```text
http://localhost:8765/vote.html?demo=1
http://localhost:8765/index.html?demo=1
```

데모는 `test/fixtures/demo-data.json`을 읽고 투표 날짜를 페이지 로드 시 이번 토요일로 바꿉니다.
화면 상단에 **데모 데이터입니다 (저장되지 않음)** 배너가 표시됩니다.
투표·취소 등 데이터 변경은 해당 페이지 메모리에만 반영되어 새로고침이나 페이지 이동으로 초기화됩니다.
이름 선택은 유지됩니다. 데모에서는 `m03`(안준호)을 선택하면 회장 도구를 미리 볼 수 있습니다.
초기 참석자는 6명이며 미투표자 조성훈을 선택해 참석하면 7명, 5v5 휴식 2명·6v6 휴식 1명이 됩니다.

전역 `ExicanData`는 `members`, `currentPoll`, `votes`, `castVote`와 회장용 `createPoll`,
`setPollCancelled`를 제공합니다. 후속 페이지용 `candidates({ from, to, menuId, includeClosed })`,
`reactions(articleIds)`, `toggleReaction(articleId, memberId)`(선택 여부 반환),
`updateCandidate(articleId, patch)`, `createMatch(row)`, `matches({ from })`, `ledger({ month })`도 제공합니다.
매칭 데모는 후보 10건과 확정 매치 1건으로 시작하며, 장부 데모 목록은 빈 배열입니다.

## 매칭 후보 대시보드

```text
http://localhost:8765/matches.html?demo=1
http://localhost:8765/index.html?demo=1
```

기본 필터는 토요일·오전·미마감이며, 점수 내림차순과 작성 시각 내림차순으로 후보를 표시합니다.
지역은 여러 곳을 고를 수 있고 포맷, 마감 포함, 미분류 보기를 바꿀 수 있습니다.
필터는 `localStorage.exican_match_filters`에 유지됩니다. 과거 날짜는 항상 제외하고,
미분류 글에는 토요일·오전 필터를 적용하지 않아 아래 별도 그룹에서 원문을 확인할 수 있습니다.
실제 모드는 오늘 이후 후보를 조회하고, 날짜가 NULL인 미분류 글은 기존 데이터 API의 추가 조회로 보충합니다.
데모는 오래된 고정 날짜가 먼저 제외되지 않도록 날짜 조건 없이 읽은 후 같은 요일의 다가오는 날짜로 치환합니다.

👍를 처음 누르면 이름을 선택하고, 다시 누르면 추천을 취소합니다. **반응한 팀원**을 누르면 이름 목록이 표시됩니다.
회장(`admin`)에게만 카드의 **관리** 패널이 나타나며 팀 화면 DOM에는 연락처·메모 입력값을 넣지 않습니다.
데모에서는 안준호를 선택하면 회장 패널을 확인할 수 있습니다. 실제 권한은 인증 역할과 Supabase RLS로 검사합니다.

관리 패널에서는 연락처·우선순위·메모와 연락 상태를 입력한 뒤 **저장**합니다.
구장비는 후보 테이블에 쓰지 않고 `localStorage.exican_candidate_costs`에 숫자 입력값만 임시 보관하여 확정 모달에 채웁니다.
**문자 문구 복사**는 날짜·시간·구장·투표 참석 인원을 반영합니다. 기본 문구와 팀명은 `js/config.js`의
`SMS_TEMPLATE`, `TEAM_NAME`에서 변경합니다. 참석 투표가 없으면 5~6명, 포맷이 없으면 5v5 또는 6v6로 표시합니다.
**문자 앱 열기**는 연락처가 있을 때만 가능하며 iOS는 `&body=`, 그 외는 `?body=`로 본문을 인코딩합니다.
앱의 작성 화면을 열 뿐 자동 전송하지 않습니다.

**확정**을 누르면 날짜·시각·구장·상대팀·구장비·포맷·메모를 확인하는 모달이 열립니다.
등록 행에는 후보 글 ID, 회장 멤버 ID, 같은 날짜의 투표 ID를 연결합니다. 등록 성공 후 후보를 확정 상태로 갱신합니다.
같은 날짜·시각의 매치는 중복을 안내하고, 등록 후 후보 상태 저장만 실패하면 **상태 저장 다시 시도**로
매치를 다시 만들지 않고 복구합니다. 종료 시각은 `HH:MM` 형식이며 자정 종료는 `24:00`으로 입력할 수 있습니다.
홈에는 상위 후보 3건과 가장 이른 예정 매치를 표시합니다.

데모 후보는 원본 카페 제목 10건을 사용합니다. 발주서의 세부 분포와 수용 기준이 상충하여,
수용 기준(기본 토요일 오전 4건 + 마감 포함 시 1건 추가)을 우선해 **토요일 오전 5건(마감 1건),
토요일 오후 1건, 일요일 1건, 평일 2건, 미분류 1건**으로 구성했습니다. 전화번호는 더미 `010-0000-0000` 1건뿐입니다.
초기 확정 매치는 토요일 08:00~10:00 도봉풋살장 6v6, 60,000원입니다.

데모 변경은 기본적으로 해당 페이지 메모리에서만 유지됩니다. **홈에서 등록 매치 확인 →** 링크로 이동할 때만
등록 매치의 공개 요약을 `sessionStorage.exican_demo_match_handoff`로 한 번 전달하고 홈에서 즉시 삭제합니다.
홈 새로고침 시 원래 픽스처로 돌아갑니다. 전달 항목에는 연락처·상대팀·메모를 넣지 않습니다.
새 매치보다 이른 기존 매치가 있으면 가장 이른 매치와 함께 **방금 등록** 요약도 표시합니다.
공용 `js/data.js`, `js/rules.js`는 변경하지 않습니다.

실제 Supabase의 조회·추천·회장 저장·매치 확정·RLS와 실제 기기의 문자 앱 연결은 **미검증**이며 Claude가 검증합니다.
로컬에서는 순수 함수와 375px 데모 화면, 조회 실패 후 재시도, 매치 생성 후 상태 저장 실패 복구를 검증합니다.

## Housekeeping 정기 작업

```bash
# 시크릿이 없으면 조회도 하지 않고 날짜와 작업 계획만 출력 (종료코드 0)
node scripts/housekeeping.js --dry-run

# SUPABASE_URL / SUPABASE_SERVICE_ROLE_KEY 환경변수 설정 후 실행
node scripts/housekeeping.js
```

시크릿이 있는 `--dry-run`은 DB를 조회하여 생성 예정 행을 출력하지만 쓰지는 않습니다.
시크릿이 없으면 **조회 생략**을 표시하며 네트워크를 전혀 사용하지 않습니다.
일반 실행의 시크릿 누락은 종료코드 2, 요청 실패나 잘못된 옵션 등 예외는 1입니다.
키는 로그에서 가립니다. 브라우저에는 service-role key를 넣지 않습니다.

1. 활동 멤버를 조회하고, 일요일 13:00 이후 다가오는 토요일의 투표가 없으면 생성합니다. 토요일 당일도 대상입니다.
2. 최근 14일 내 마감된 미취소 투표에서 미투표·지각 멤버의 벌금 행을 요청합니다. 회장도 대상이며 기장일은 마감일(KST)입니다.
3. 이번 달 1일자로 월회비와 부상 면제 행을 요청합니다. 부상 기간은 양 끝 날짜 포함 28일 이상이고 해당 월에 하루 이상 겹치면 면제합니다. 시작·종료일이 모두 필요합니다.

금액과 면제율은 `js/config.js`만 사용합니다. PostgREST 요청은
`Prefer: resolution=ignore-duplicates,return=minimal`과 `on_conflict`를 사용합니다.
충돌 컬럼은 투표 `match_date`, 벌금 `member_id,category,ref_poll_id`, 회비 `member_id,category,entry_date`입니다.
요약의 행 수는 요청 대상 수이며 실제 신규 저장 수는 그 이하입니다.
`cron.yml`은 기존 scrape 뒤에 `if: ${{ !cancelled() }}`로 실행하므로 scrape 실패 후에도 실행합니다.

**실제 Supabase 경로는 미검증이며 Claude의 검증이 필요합니다.** 특히 현재 저장소의 장부 unique index는
조건부(partial) 인덱스입니다. PostgreSQL은 partial index 추론에 대응하는 predicate가 필요하므로,
발주서대로 컬럼만 지정한 `on_conflict` 요청은 현재 스키마에서 `42P10`으로 실패할 가능성이 있습니다.
요청 형식 테스트 통과는 실제 DB 멱등성 검증을 의미하지 않습니다. 발주서의 변경 금지에 따라 `supabase/*`는 유지했습니다.
실제 실행 전에 Claude가 인덱스/쓰기 경로 호환성을 해결하고 두 번 실행하여 중복이 없는지 확인해야 합니다.
근거: [PostgreSQL ON CONFLICT](https://www.postgresql.org/docs/current/sql-insert.html#SQL-ON-CONFLICT),
[PostgREST on_conflict](https://docs.postgrest.org/en/stable/references/api/tables_views.html#on-conflict).

## 카페 수집기

Node 20 이상에서 네이버 카페 게시판 4곳의 **글 목록만** 읽고 제목을 파싱합니다. 메뉴와 카페 ID는
`js/config.js`의 `CAFE` 설정을 사용하며, 외부 패키지 설치는 필요하지 않습니다.

```bash
# 오프라인 확인: 네이버와 Supabase에 접속하지 않음
node scripts/scrape-cafe.js --dry-run --input test/fixtures/api-menu-623.json --menu 623

# 온라인 확인: 기본 4개 메뉴 × 2페이지, Supabase 저장 없음
node scripts/scrape-cafe.js --dry-run
node scripts/scrape-cafe.js --dry-run --menus 623,625 --pages 1

# 환경변수 설정 후 실제 수집 및 저장
node scripts/scrape-cafe.js
```

| 옵션 | 동작 |
|---|---|
| `--dry-run` | 점수 내림차순 표와 메뉴별 요약만 출력. Supabase 환경변수 불필요 |
| `--input <file>` | JSON 응답 파일 1개를 메뉴 1개 분량으로 사용. 네트워크 차단을 보장하도록 `--dry-run`과 함께 사용 |
| `--menu <id>` | 파일 입력의 메뉴 ID와 이름 지정. 생략하면 첫 글의 `menuId` 사용, 빈 목록은 필수 |
| `--menus <ids>` | 수집 메뉴 제한(쉼표 구분). 기본값은 `CAFE.MENUS`의 전체 메뉴 |
| `--pages <1\|2>` | 메뉴당 페이지 수. 기본 2페이지, 페이지당 30건. 파일 입력에서는 적용하지 않음 |

실제 저장에는 환경변수 `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`가 모두 필요합니다.
GitHub 저장소의 Actions Secrets에도 **동일한 이름**으로 등록하며, 값은 소스나 실행 인자에 넣지 않습니다.
`.github/workflows/cron.yml`은 KST 06:00~24:00 매시 정각에 실행되도록 예약되고,
Actions의 **Cron → Run workflow**로 수동 실행할 수 있습니다. 작업 제한은 10분이며 동시 실행은 직렬화합니다.

수집기는 메뉴별로 처리하며 하나가 실패해도 나머지 메뉴를 계속합니다. 하나 이상 성공하면 종료코드 0,
모든 메뉴 실패는 1, 필수 환경변수 누락이나 옵션 오류는 2입니다. 파일을 읽거나 해석하지 못하면 1입니다.
요약의 `fetched`는 수신한 글 수, `parse_ok`·`closed`는 중복 제거 후 글 수, `upserted`는 저장 완료 수입니다
(`--dry-run`은 0). 페이지 간 같은 글은 앞 페이지 값을 한 번만 반영합니다.

저장은 `article_id` 기준으로 100행씩 upsert하며, 수집기 소유 컬럼만 전송합니다.
`first_seen_at`, `phone`, `contact_status`, `memo`, `our_priority`, `admin_updated_at`, `created_at`은
본문에서 제외해 최초 기록과 회장 입력값을 보존합니다. 키와 토큰은 출력하지 않습니다.
자동 테스트는 모두 오프라인으로 실행합니다. 실제 네이버 접속과 Supabase upsert는 Claude가 별도 검증합니다.

## 장부

`ledger.html`은 팀 로그인 후 월별 회비·벌금·면제·환급·납부 상태를 보여줍니다.
내 이름과 **내 항목만**으로 개인 항목을 찾고, 멤버 행을 누르면 날짜·메모·정산 여부를 펼칩니다.
팀 잔액은 전 기간의 정산 완료 행과 팀 단위 행을 한 번씩 합산합니다.
월별 미납 합계와 미납자 수는 개인별 미정산 합계가 양수인 멤버만 포함합니다.
음수 합계는 **받을 돈**이며 다른 멤버의 미납을 차감하지 않습니다.
회비·벌금은 양수, 면제·구장비·간식·플랩 지원은 음수입니다. 면제는 환급 열에 중복 합산하지 않습니다.
`teamSummary`의 `income`/`expense`는 조회 월 전체 기록의 양수 합/음수 절댓값 합이고, `balance`는 월과 무관합니다.

팀원은 최근 4주 매치를 선택해 간식을 청구하고 대기·승인·거절 상태를 확인합니다.
회장은 펼친 항목의 **선택 정산**, 멤버별 **전부 정산**, 벌금·구장비·플랩 지원·입금·조정 기록,
회장 면제와 간식 승인을 처리합니다. 전부 정산은 조회 월에만 적용합니다.
회비·벌금을 납부했을 때는 기존 행을 정산하며, 별도의 **입금** 기록은 기타 수입에만 사용해 중복 계산을 피합니다.
구장비는 팀 단위, 플랩 지원은 개인별 월 1회입니다. 매치를 고른 벌금은 경기 날짜를 사용하고,
매치 없는 수동 기록은 입력한 날짜를 사용합니다. 회장 면제는 설정의 주/월 모드에 따라 중복을 막습니다.
청구 승인 시 환급 행을 먼저 만들고 승인 상태를 저장해, 실패 후 재시도해도 같은 매치·구매자의 간식 행을 중복 생성하지 않습니다.
실제 쓰기 권한은 Supabase RLS가 검사하며 권한 거부는 회장 로그인 안내로 표시합니다.

```text
http://localhost:8765/ledger.html?demo=1
http://localhost:8765/index.html?demo=1
```

데모 이름 **안준호(m03)**는 회장, 다른 이름은 팀원으로 동작합니다. 데이터 변경은 페이지 메모리에만 남고
새로고침·페이지 이동 시 초기화됩니다. 006의 매치 데이터가 없어도 장부가 참조하는 데모 경기 두 개를 선택할 수 있습니다.
다른 데모 키는 수정하지 않으며 실제 모드에서는 `matches`의 등록 경기만 사용합니다.
초기 2026-10 데이터는 정산된 회비 8명 × 30,000원 − 구장비 60,000원 = 팀 잔액 **180,000원**입니다.
미납자는 m05 35,000원, m09 40,000원, m10 30,000원, m12 30,000원으로 **4명 / 135,000원**입니다.

실제 회비 자동 생성 시작 월은 `LEDGER_START_MONTH`를 따르며 이 작업에서는 변경하지 않습니다.

`python -m http.server 8765` 실행 후 `admin.html?demo=1`, `member.html?demo=1&id=m05`, `rotation.html?demo=1`, `rules.html?demo=1`로 접속합니다. 안준호는 데모 회장, 권형관은 팀원입니다.

### 해석 및 검증 범위

- 발주서의 데모 연동 버튼 비활성 문구보다 데모 불러오기·저장 수용 기준을 우선했습니다. 실제 설정 전·비로그인에서는 수동 배정을 유지하고 연동 버튼을 비활성화합니다.
- `attendanceRate`의 첫 인자는 투표와 연결된 완료 매치 행(또는 `match_id/status/match_date`를 합친 투표 행)입니다. `polled`는 최근 12주의 완료 경기 수, `attended`는 그 경기 중 출석·지각·경기 후 도착 수, `rate`는 0~1 비율입니다. 취소·예정·미래 경기는 제외하며, 투표 선택과 무관하게 실제 출석을 집계합니다. 투표 참여율은 별도로 표시합니다. 테스트용 마지막 `todayKst` 인자로 날짜를 고정할 수 있습니다.
- `out_quarters`는 기존 배정 알고리즘과 같은 **키퍼 또는 휴식 쿼터 번호**입니다. `active_quarters`는 실제 참가 구간의 쿼터 수이며, `rotationTotals.outQuarters`는 전체 키퍼·휴식 쿼터 수입니다.
- 새 멤버 ID는 기존 최대 번호+1입니다. 동시 생성으로 기존 멤버가 덮어써지지 않도록 신규는 insert, 기존은 ID 기준 upsert합니다.
- 출석의 ‘해당 없음’은 기존 행을 삭제하지 않습니다. 저장된 행은 출석/사유 불참 등으로 정정합니다. 배정 기록도 `(match_id, member_id)`로 upsert하며 누락 행을 삭제하지 않습니다.
- 현재 DB unique index는 NULL `member_id`인 구장비의 동시 중복을 막지 못합니다. 관리 확장은 저장 전에 같은 매치 구장비를 조회해 중복을 차단하지만, 동시 요청의 원자적 방지는 후속 스키마 보완이 필요합니다. 이번 작업은 `supabase/*`를 수정하지 않습니다.
- 지난 경기 픽스처 추가에 맞춰 변경 파일 목록 밖 `test/housekeeping.test.js`의 마감 경계 입력을 해당 투표 한 건으로 한정했고, `test/ledger-rules.test.js`의 원본 불변 검사는 호출 전후 비교로 보정했습니다. 기존 검사 의도와 제품 코드는 유지합니다.
- 자동 테스트는 기존 436개 + 신규 27개 = **463개**입니다. 375px 데모와 권한 전환·중복 기록·장부 반영을 브라우저에서 확인했습니다. 실제 Supabase의 RLS·조회·쓰기는 **미검증**이며 Claude가 검증합니다.

| 참가자 수 | 포맷 | 필드 인원(키퍼 포함) | 키퍼 | 휴식 |
|----------|------|----------------------|------|------|
| 6명 | 5v5 | 5 | 1 | 1 |
| 6명 | 6v6 | 6 | 1 | 0 |
| 7명 | 5v5 | 5 | 1 | 2 |
| 7명 | 6v6 | 6 | 1 | 1 |

기본 기준은 8쿼터입니다.
키퍼·휴식을 합친 out 배정은 참가 구간의 시작·끝과 out 사이의 필드 플레이 길이가 고르게 되도록 점수를 매깁니다.
연속 out 방지와 참가 쿼터 대비 횟수 공평성을 우선하며, 역할별 횟수와 out 간격도 함께 고려합니다.
횟수가 같은 후보는 마지막 out 이후 오래 뛴 선수를 우선하고, 같은 입력과 다시 섞기 횟수에는 같은 결과를 제공합니다.
개인 간격 점수가 1.0을 넘으면 결과에 `out 간격 편중` 경고와 해당 쿼터를 표시합니다.
